# DAYCORD — DC-001

## Architecture Decision Record

**Project:** Daycord

**Status:** Accepted

**Purpose:** Establish architectural boundaries, technology choices,
and fundamental domain design decisions for Daycord.

## 1. General Architecture

Daycord is a local cross-platform desktop application built with
C# and .NET 10.

The application uses Avalonia UI 12.

Architecture: modular monolith.

Solution format: Daycord.slnx.

Projects:

1. Daycord.Core
2. Daycord.Infrastructure
3. Daycord.Desktop

The Desktop project contains the application entry point.

No separate HTTP backend is required.

## 2. Dependencies

Allowed dependencies:

- Infrastructure → Core
- Desktop → Core
- Desktop → Infrastructure

Core must not depend on Infrastructure or Desktop.

Circular dependencies are prohibited.

## 3. Daycord.Core

Contains domain entities and application contracts.

### TaskItem

Represents a user task.

Properties:

- Id: Guid
- TaskDate: DateOnly
- Title: string
- ShortDescription: string?
- DescriptionMarkdown: string?
- StatusId: Guid
- CreatedAtUtc: DateTime
- UpdatedAtUtc: DateTime
- CompletedAtUtc: DateTime?

TaskDate is the primary task date.

Changing TaskDate must not automatically change planning
or work entries.

### TaskStatusDefinition

Task statuses use an extensible domain model.

Properties:

- Id: Guid
- SystemKey: string?
- Name: string
- IsSystem: bool
- IsCompleted: bool
- SortOrder: int

Built-in statuses:

Open:

- SystemKey: open
- Id: 5e8a148e-1a3b-4b17-bba6-251392a01d61
- IsCompleted: false

Completed:

- SystemKey: completed
- Id: b9436dc3-7247-4d9e-a032-2a9cb1b9c7a8
- IsCompleted: true

User-defined statuses are supported by the database design.

The status editor is outside DC-003.

### PlanningPeriod

Represents planned work time.

Properties:

- Id: Guid
- TaskId: Guid
- PlannedDate: DateOnly
- PlannedMinutes: int

A task may have multiple planning periods.

PlannedMinutes must be positive.

Planning records are independent of actual work entries.

### WorkEntry

Represents actual work.

Properties:

- Id: Guid
- TaskId: Guid
- WorkDate: DateOnly
- ActualMinutes: int
- WorkDescription: string?
- Note: string?
- CreatedAtUtc: DateTime
- UpdatedAtUtc: DateTime

ActualMinutes must be positive.

Work entries are the source of actual worked time
for future reports.

## 4. Domain Principles

- Durations are stored in integer minutes.
- Planning does not automatically create actual work entries.
- Actual work does not automatically modify planning.
- Dates use DateOnly.
- Technical timestamps use UTC.
- Markdown content is stored as source text.
- Domain classes are independent of Avalonia and SQLite.
- Task statuses use identifiers rather than a fixed enum.

## 5. Daycord.Infrastructure

Infrastructure implements technical services and persistence.

Approved persistence stack:

- SQLite
- Microsoft.Data.Sqlite 10.0.13
- Dapper 2.1.89

Entity Framework Core is not used.

### Database Location

The database is stored in the operating system's
LocalApplicationData directory.

Filename:

`daycord.db`

The application never stores its working database
inside an installation directory or application bundle.

### Connections

Database connections are short-lived.

Foreign key enforcement is enabled.

A reasonable busy timeout is configured.

The Desktop ViewModels do not manage SQLite connections.

### Type Serialization

Guid:

TEXT using normalized D format.

DateOnly:

TEXT using yyyy-MM-dd.

DateTime UTC:

TEXT using unambiguous ISO 8601 UTC representation.

Integer durations:

INTEGER using whole minutes.

Dapper-specific conversion logic belongs to Infrastructure.

### Migration System

Migrations are versioned SQL scripts embedded
in the Infrastructure assembly.

Migration history is stored in:

`__SchemaMigrations`

Fields:

- Version
- Name
- Checksum
- AppliedAtUtc

Each migration is applied only once.

Checksums detect changes to published migration scripts.

Unknown or newer schema versions must not be downgraded.

Schema updates and their migration history records
are executed transactionally.

Failed initialization blocks database-dependent functionality.

### Migration 001

File:

`001_InitialSchema.sql`

Creates:

- TaskStatuses
- Tasks
- PlanningPeriods
- WorkEntries
- Required indexes
- Foreign keys
- CHECK constraints
- Built-in task statuses

Published migration 001 is immutable.

### Migration 002

File:

`002_NormalizeMigrationUtcTimestamps.sql`

Normalizes the historical migration 001 timestamp.

The previous implementation supplied DateTime.UtcNow
directly as a SQLite parameter, resulting in a timestamp
without an explicit timezone designator.

The reworked migration runner validates recognized
historical timestamps before applying migration 002.

Unknown formats cause initialization to fail safely.

Recognized historical values are converted using
a text transformation that preserves their fractional digits.

New migration history timestamps are written explicitly
as ISO 8601 UTC strings with Z.

Migration 001 is not modified.

### Migration Safety

Before upgrading an existing recognized schema,
the application creates a consistent protective backup.

Backup mechanism:

`SqliteConnection.BackupDatabase()`

Backup location:

`Backups/SchemaUpgrades`

Backups are not automatically removed after upgrades.

Database initialization includes:

- Migration checksum validation
- Required schema validation
- System status validation
- UTC timestamp validation
- PRAGMA integrity_check
- PRAGMA foreign_key_check

An unknown existing database is not overwritten.

The application does not automatically restore backups
over existing potentially damaged files.

## 6. Daycord.Desktop

Uses:

- Avalonia UI
- CommunityToolkit.Mvvm
- Microsoft.Extensions.DependencyInjection

UI architecture: MVVM.

Composition Root is located in Desktop.

MainWindow receives MainWindowViewModel through DI.

The database is initialized asynchronously after
the main window opens.

The initialization process has three states.

### Initializing

Message:

`Initializing local database...`

DatabaseReady:

false.

### Ready

Message:

`Local database ready.`

DatabaseReady:

true.

This state is set only after successful initialization.

### Failed

Message begins with:

`Database initialization failed:`

DatabaseReady:

false.

The error is displayed to the user.

Database-dependent functionality remains unavailable.

No blocking Wait() or Result() call is used on the UI thread.

## 12. DC-003 Rework

The rework addresses two identified issues.

### Startup Status

The user interface must show database initialization
state through MainWindowViewModel.

Previously displayed Russian placeholder messages
must not remain in the startup interface.

The Ready state is shown only after successful
database initialization.

Failures are visible to the user.

### Migration UTC Representation

Migration history timestamps must contain an explicit
UTC designator.

New rows use invariant ISO 8601 UTC strings.

Migration 002 upgrades the recognized historical
timestamp from the original implementation.

The original migration SQL and checksum remain unchanged.

Unknown timestamp formats must not be automatically
interpreted as UTC.

Existing user databases must not be deleted, overwritten,
or modified manually to perform verification.

## 13. Verification Policy

Automated unit-test projects are excluded from the MVP.

Manual and isolated integration checks are required.

Tests of migrations, errors, constraints, and backups
must run against isolated databases.

The production database must remain untouched during
destructive or error-injection verification.

Verification results must distinguish:

- Implemented behavior
- SQL-only verification
- Actual .NET runtime verification
- Platform-specific verification

Unverified acceptance criteria must not be reported
as Passed.

Further functionality requires a separately approved task.
